# 业务场景与程序不匹配清单

记录日期：2026-11-13
代码基线：wechat-msg-mcp main 分支 92372b5
用途：业务复盘后的待修清单。本文不含真实群名、学员姓名、账号与金额信息，可直接入库。

## 一、业务场景

围绕「用AI解锁50个人生第一次」活动，每位学员对应一个专属小群，活动每周发布 1-3 次体验教程，学员进度差异很大。需要 Agent 每天做的事：

1. 扫描在训学员群过去 1-3 天的新消息
2. 识别学员的进展、疑问、交付截图、押金与付款相关对话
3. 按人汇总出画像与待办，生成跟进建议
4. 偶尔做跨群横向对比，看谁活跃、谁掉队

数据来源是本机微信 4.x 的解密库，通过 MCP 只读查询。

## 二、一句话结论

程序默认按时间升序取最早的 N 条，且截断时不给任何信号；业务要的却是最新进展。方向相反，于是漏消息成为默认结果，而不是意外。

## 三、不匹配清单

| 编号 | 业务动作 | 程序现在的行为 | 业务后果 | 期望行为 | 代码位置 |
|---|---|---|---|---|---|
| M1 | 查某群某时间段的消息 | ORDER BY local_id ASC LIMIT N，返回窗口内最早的 N 条 | 只看到这段时间的开头，后面的消息全部丢失 | 默认从最新往回取，或提供 newest_first 开关 | src/db/reader.py:676-687 |

## 四、实测证据（已脱敏）

1. 某个 11 月新开学员群，11-11 起共 59 条消息。limit=10 时返回 11-11 09:43 至 11-12 13:11 的 10 条，头部写「共 10 条」，没有任何截断提示；改用 limit=10 offset=55 才拿到最后 4 条（11-12 13:59 至 14:14）。
2. 复盘的那次会话共 238 次微信工具调用，其中 get_chat_history 168 次、search_messages 17 次、get_recent_messages 10 次、list_contacts 13 次；offset 参数使用 0 次。
3. 同一会话出现 50 次「没有找到聊天记录」，逐条回查数据库，全部是该群在窗口内确实没有消息（最后一条停在 11-08 至 11-10），属于真实空群，不是误报。这一条说明程序的问题不是「把有消息说成没消息」，而是「有消息也只给一部分」。
4. 一次 get_recent_messages(25 个群, days=3, limit=500) 返回 MCP error -32001，AI 随即改为逐群调用；同参数事后重试成功（183 条），说明是偶发超时，但它把流程推向最容易漏数据的路径。
5. 数据新鲜度：会话记录显示 AI 发现数据停在昨日，重启微信并重新解密后，服务才读到当天 21:15 的会话。

## 五、修复优先级

| 优先级 | 条目 | 理由 |
|---|---|---|
| P0 | M1、M2、M3 | 直接决定漏不漏，改动集中在一条 SQL 与一处返回头 |
| P1 | M4、M5、M8 | 决定「漏了知不知道」，把静默失败改成显式失败 |
| P2 | M6、M7、M9 | 扩展业务场景：跨群、周月统计、大响应控制 |
| P3 | M10 | 新数据面：文件与导出 |

## 六、验收标准

| 条目 | 验收方法 |
|---|---|
| M1 | 对窗口内 59 条消息的群，limit=10 应返回最新 10 条，最早一条时间落在 11-12 14:14 附近 |
| M2 | 返回体包含 total、returned、has_more，数值与直接查库统计一致 |
| M3 | 构造历史横跨两个 message 分库的会话，offset 从 0 翻到末页，各页条数之和等于总数且 local_id 无重复 |
| M4 | 25 个群、3 天窗口，单次调用完成或明确分批返回，失败会话单独列出 |
| M5 | 用旧群名查询时返回候选列表，不再返回空结果 |
| M8 | 返回体头部带数据截止时间，与 F:/xwechat_files 下最新 mtime 对比 |
| M9 | 传 inline_media=false 时返回体小于 20KB，媒体以路径或引用形式给出 |

## 七、不属于程序问题的情况

- 群里确实没消息：本次核对的 50 次空结果全部真实。
- 微信未落盘：还在 WAL 里未 checkpoint 的消息，任何读取方式都看不到，只能等微信切换窗口或重启。
- 学员换群或改名：旧群的历史仍留在旧群，程序不负责合并身份。
