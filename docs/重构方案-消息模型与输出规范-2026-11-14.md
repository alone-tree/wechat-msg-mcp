# 方案：消息模型与输出规范（2026-11-14）

状态：已实施（提交 9dd2156，98 项单测通过）。实施中的取舍与偏差记在文末「实施记录」。

依据用户当天定的四条原则：

1. MCP 与 CLI 是两个用途：MCP 给 AI 在对话里查常用信息，CLI 给脚本做批量与复杂跨表。工具面保持简单，复杂查询由 AI 自己写脚本调 CLI。
2. 消息不标收发方向，我发的就是 out、别人发的就是 in，冗余；重点是把「谁发的」和「发了什么」标清楚，系统消息也要能读懂。
3. 群名为空时用成员名兜底，与微信客户端显示效果一致。
4. 统一一套变量命名规范。

## 0 定位与边界

| 项 | MCP | CLI |
|---|---|---|
| 面向 | AI 在对话里做查询与判断 | 脚本、批量、跨表聚合 |
| 默认详细度 | lite（可传 full） | full |
| 默认序列化 | 紧凑 JSON | NDJSON，一行一条 |
| 落盘 | 超阈值自动落盘（text/json/csv） | --format 指定 |
| 不做 | 复杂聚合、跨表 join、批量汇总 | 交互式阅读 |

新增约定：复杂能力走 CLI 子命令，不往 MCP 加工具。例如「按成员组合找群」用 `wechatq groups --members A,B,C`，MCP 只保留七个常用工具。

## 1 命名规范

| 类别 | 规则 | 示例 |
|---|---|---|
| 风格 | snake_case，全小写；只允许 id、url、db、md 四个缩写 | chat_id、db_name |
| 消息时间 | 唯一不带后缀的时间字段，就叫 time（它就是消息发生时刻） | time |
| 其他时刻 | 一律 `*_at` | last_active_at、joined_at、updated_at |
| 数据截止 | 顶层统一 `data_until`（原 data_cutoff 改名） | data_until |
| 计数 | 实体固有数量用 `*_count`；查询命中总数用 `total` | member_count、like_count、total |
| 布尔 | `is_*` / `has_*` / `can_*` | is_friend、has_more、can_open |
| 分页四件套 | 固定 total、returned、has_more、next | next 承载游标或 offset |
| 标识 | 自身用 id；他人用 `*_id` | id、chat_id、sender_id、owner_id |
| 类型 | 用户可见语义用 type；原始数值只在 raw 档叫 local_type | type=image |
| 名称四件套 | name（显示名）、remark、nickname、alias（微信号） | |
| 错误 | ok=false，error{code, message, candidates} | code=chat_not_found |

媒体对象统一键：kind、source、bytes（体积，不是数据本体）、path、size、width、height、duration（秒）、url、title、desc、missing_reason。

## 2 消息模型

去掉 direction。理由：sender 已标识来源，方向由「from 是否为自己」直接推出；当前 direction 依赖 real_sender_id 解析，解析失败时会给出错误方向（CLI 路径实测全判 in）。

lite 档（MCP 默认）：

| 字段 | 说明 |
|---|---|
| id | 会话内 local_id |
| time | 发送时间 |
| from | 发送者显示名；自己发的固定「我」 |
| text | 自足正文，见下 |
| media | 仅非纯文本时出现，含 kind 与必要字段 |

full 档追加：sender_id、type、subtype（仅 app 类）、chat_id、chat_name、media 明细、senders 表。

raw 档：保留 local_type、原始 XML 等全部字段，仅供排查。

text 的自足规则：

| 消息类型 | text 内容 |
|---|---|
| 文字 | 原文 |
| 图片 | 空（media.kind=image 已足够，渲染器补 [图片]） |
| 表情 | [表情] |
| 语音 | 转写全文，取消 voice_text 字段；无转写时 [语音 12 秒] |
| 视频 | [视频 12 秒] |
| 文件 | [文件 简历.pdf] |
| 链接 | 标题（原文 URL 放 media.url） |
| 转账 | [转账 257.00 元] |
| 红包 | [红包] |
| 引用 | 原话，另带 quote{from, text} |
| 系统 | [系统] 一句话，见第 3 节 |

## 3 系统消息折叠

MCP 与 CLI 默认都不再输出 XML 原文（raw 档保留）。折叠规则按 sysmsg 类型：

| 原始类型 | 折叠成 |
|---|---|
| revokemsg | [系统] 某某 撤回了一条消息 |
| sysmsgtemplate 邀请 | [系统] 某某 邀请 某某 加入了群聊 |
| sysmsgtemplate 改名 | [系统] 某某 修改群名为 某某 |
| sysmsgtemplate 其他 | [系统] + 模板去标签后的一句话（截断 80 字） |
| plain（非 XML） | [系统] + 原文 |
| 拍一拍（当前被误判成 app/channels） | [系统] 某某 拍了拍 某某，修正分类 |
| 未知结构 | [系统] + 去标签摘要 80 字，raw 留原文 |

from 规则：系统消息的 from 留空（不写群 id，不写「我」），动作主体写在 text 里。

## 4 群名兜底

name 为空时（当前 163/776 个群属于这种），按微信客户端同样思路用成员昵称拼接：

| 情况 | name 值 | name_source |
|---|---|---|
| 有备注 | 备注 | remark |
| 有群昵称 | 群昵称 | nickname |
| 都没有 | 前 3 个非自己成员昵称 + 「等 N 人」 | members |
| 连成员都取不到 | 「群聊」 | fallback |

full 档附 members_digest（成员昵称数组），便于核对。排序按 chatroom_member 表顺序，与客户端一致；截断到 3 人是我们的取舍，需拿 5 个无名群与客户端截图对照后再定案。

## 5 三档详细度与两个出口

一套 schema，两个渲染：

| 档 | 用途 | 谁默认用 |
|---|---|---|
| lite | 对话内读，字段最少且自足 | MCP |
| full | 需要精确判断、要 sid 与明细 | CLI 默认、MCP 传参 |
| raw | 排查，保留全部原始字段 | 手动 |

CLI 序列化：默认 NDJSON（一行一条消息，含 chat 字段），--json 输出紧凑 JSON 信封，--pretty 缩进，--format text 输出人读分节文本。MCP 输出同一信封的 JSON。

## 6 导出格式

| format | 适用 | 形态 |
|---|---|---|
| text | 人读、给队友 | 按会话分节，一行一条，多行正文缩进续写 |
| md | 人读 | 同样分节，不用表格；仅在字段固定且无换行时用表格 |
| csv | 程序 | 固定列，剔掉全空列 |
| json / ndjson | 程序 | 同一信封 |

现有 md 的 11 列表格实测会被正文换行撑断（30 条导出成 33 行），且 media 列是 Python 字典串，本次改掉。

## 7 一并修复的缺陷

| 项 | 现状 | 改法 |
|---|---|---|
| CLI self 为空 | CLI 不读 WECHAT_FILES_DIR 就直接放弃 | get_account_wxid 兜底走微信目录探测；认不出时 from 用真实昵称并给 warnings |
| 方向字段不可信 | real_sender_id 为空即判为自己 | 去掉 direction；sender 解析失败时 from 留空并标 unknown_sender |
| 多目标静默截断 | 每群最多 50 条且不告知；第二页 0 条却 has_more=true | has_more 按游标过滤后剩余算；被截断的会话在 warnings 点名；per_target_limit 暴露 |
| types 不校验 | transfer 静默 0 条 | 未知值报错并给 valid；补 app:transfer 等别名 |
| output=file 只导当前页 | limit=2 时只导 2 行 | 导出即翻页到 limit 或 total，export 里标 is_partial |
| senders 混入群 id | 系统消息把群 id 当发送者 | 系统消息不进 senders |
| 拍一拍分类错 | 显示成 app/channels | 归入 system，按第 3 节折叠 |
| 每次调用 0.77 秒固定开销 | load_contacts 0.31 秒 + 发送者表重建 | 进程内按库 mtime 缓存联系人索引与发送者表 |
| CLI 入口没装 | 文档写 wechatq，实际只有 wechat-mcp.exe | 打包 CLI 入口或文档改成 python -m src.cli |

## 8 分阶段与验收

| 阶段 | 内容 | 验收 |
|---|---|---|
| A 规范落地 | 命名规范文档、lite/full/raw schema 定义 | 文档评审通过，schema 表与代码字段一一对应 |
| B 消息模型 | 去 direction、text 自足、系统折叠、拍一拍归类 | 抽 300 条真实消息：from 覆盖率 100%，system 文本 0 条含 XML，拍一拍全部归 system |
| C 群名兜底 | name_source 与 members_digest | 5 个无名群与微信客户端截图逐一对照 |
| D 出口统一 | render(envelope, detail, format)、CLI NDJSON 与 text、CLI self 修复 | 同一查询 MCP 与 CLI 字段集合一致，CLI self 非空 |
| E 分页与校验 | has_more 修正、per_target_limit、types 校验、导出翻页 | 28 群场景翻页可取满 total；未知 types 报错 |
| F 导出重做 | text/md 分节、CSV 剔空列 | 含换行与竖线的消息导出后结构完整 |
| G 性能 | 联系人/发送者缓存 | 单次调用 < 0.3 秒；127 群脚本 < 30 秒 |

## 9 不做

| 项 | 原因 |
|---|---|
| 新增批量摘要工具 | 按新原则属于脚本职责，AI 自己调 CLI 更快 |
| 按成员组合找群进 MCP | 同上，做成 CLI 子命令 wechatq groups --members |
| 推翻统一信封一次到位 | 现有 service 已统一，只加档位与渲染，不做大迁移 |
| 保留 direction 兼容字段 | 保留等于继续输出不可信数据，一次删净并在文档标明 |

## 10 实施记录

A 到 G 七个阶段随提交 9dd2156 一次落地，单测从 66 项加到 98 项。各阶段实测结果：

| 阶段 | 实测结果 |
|---|---|
| A 规范落地 | data_cutoff 全仓改名 data_until，next_cursor 与 next_offset 统一成 next，所有信封加 ok，错误结构改成 error{code, message, candidates}；文档与代码字段逐项对齐 |
| B 消息模型 | 抽最近 200 条：system 文本 0 条含 XML，非系统消息 from 覆盖率 100%，拍一拍全部归 system；CLI 路径 from 与自建账号识别正常 |
| C 群名兜底 | 776 个群里 163 个原本名为空，实施后 remark 50、nickname 563、members 159、fallback 4（4 个都是已被移出的群）|
| D 出口统一 | MCP lite 与 CLI full 字段一致；CLI 认回本机 wxid，self 不再为空；CLI 默认 NDJSON |
| E 分页与校验 | 28 个群、limit=200 连续两页各 200 条，total 15107 可信；types=["nonsense"] 报错并给 candidates，types=["transfer"] 查出 14 条 |
| F 导出重做 | 含换行与竖线的消息导出 md 与 text 结构完整；csv 剔掉全空列，media 与 quote 压成短 JSON；output=file 翻页取满 |
| G 性能 | 单次查询 0.77 秒降到 0.14 到 0.2 秒；28 个群跨 15107 条命中的单页查询约 2.9 秒 |

实施中与原方案有出入的地方：

| 项 | 方案原定 | 实施结果与原因 |
|---|---|---|
| text 占位 | 图片等 text 留空，由渲染器补「[图片]」 | 改成 text 直接给占位。方案本身要求 text 自足，留空得靠消费者记住补什么，容易丢信息 |
| per_target_limit | 默认 50 并暴露 | 默认 0 等于 limit。原值 50 会让翻页也拿不到被丢掉的行，与「翻页取满」直接冲突；显式传值且小于 limit 时才截断，并在 warnings 点名 |
| 视频媒体字段 | 沿用 video_path 等 | 改成 path（mp4）、size、exists，封面单独 cover_path。原名带前缀，不符合第 1 节命名规范 |
| 导出上限 | 翻页到 total | 最多 200 页或 20 万行，超出标 is_partial。防止一次导出把进程拖死 |
| 报告模块 | 未提及 | annual 与 metrics 里的 data_cutoff 一并改名，避免同一个词两种写法 |

未验证与遗留：

| 项 | 状态 |
|---|---|
| 群名兜底的截断与「等 N 人」写法 | 未与微信客户端截图对照。客户端用的是群昵称，本地只有备注与昵称，个别字可能不同 |
| 视频 mp4 原件导出 | 未实测。本地有 mp4 时 path 直接指向，extract_media 复制链路实测过的是封面与文件消息 |
| CLI --format html | 仍是旧表格渲染，没有按新消息模型重做 |

附带发现：session.db 的 SessionTable.last_sender_display_name 存着每个会话最后一条消息发送者的群内显示名，这是本地唯一能碰到群昵称的地方，只覆盖最后一条，未接入。
