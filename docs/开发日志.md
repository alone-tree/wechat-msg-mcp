## 2026-11-14

- 独立验收发现活跃群图片整体读不到（6 个群 77 张，0 张可用），定位到两处结构性问题。其一，图片定位只认 hardlink 登记表，而微信 4.x 把新落盘的文件名写进了 message_resource.db 的 MessageResourceInfo.packed_info，登记表里根本没有这些行。其二，验收还发现失败图片的缩略图其实在盘上且能解密（解出长度与消息 XML 的 cdnthumblength 逐一相等），工具完全不去找。结论：不是数据没有，是找法只覆盖了一种情况。
- 修复：图片与视频改成三级定位。第一级按 message_resource 的消息到落盘基名映射（新增 src/db/resource.py，protobuf 取 field 2 里的 field 1），第二级查 hardlink 登记表，两条来源合并、原图与高清排在缩略图之前，第三级按消息 XML 自带的 length、cdnthumblength、cdnthumbwidth/height 在磁盘上认文件（体积窗口 31 到 47 字节，再用宽高复核）。三级都不中才算本地没有，missing_reason 统一为 no_local_image，不再用会误导的 hardlink_row_missing。
- 顺带修三处。视频封面同样加三级定位，此前 0/3 全部 cover_missing；长截图按长边压会被压成几十像素宽（860x14040 压到 98x1600，一个字看不清），改为长宽比超过 3 时保底宽 600、总高不超过 12000，返回时按 1600 高切段并给 media.tiles，整图另存 media.path；整段异或改用 translate 表，几十万像素的图不再逐字节跑 Python 循环。
- 实测（最近 7 天 296 张图片抽样）：修复前 124 张可读（全部原图），修复后 166 张原图加 129 张缩略图，共 295 张可读（99.7%），只剩 1 张本地确实没有。验收报障的三个群从 15/15 全失败变为 15/15 全成功，视频封面从 0/3 变为 3/3。代价是每张约 0.1 到 0.3 秒（原图要解 HEVC 首帧），50 张整页约 10 到 15 秒。
- 另外补齐 refresh 字段稳定性：TTL 跳过分支现在同样带 failed、failed_detail、shadow，不再只在刷新分支出现；文件消息缺盘时补 missing_reason=no_local_file，与图片口径一致。

- 发言人信息重构（用户需求）：start 与 get_messages 返回里加 self 字段（账号 wxid、昵称、微信号、区分收发的说明）；每条消息只保留 sender_name 与 direction（自己发的是「我」加 out），把 sender_id 收进结果尾部的 senders 映射表（键是 wxid，值含 name、nickname、alias、friend）。目的是让 AI 一眼分清谁发的，同时避免每条消息重复长 ID。实测：self 给出子柯/zk-Bai，senders 正确列出大爷与哥的昵称和微信号，自己发的消息 direction=out、sender_name=我。

- 修「收到的图片读不到」：现象是同一群里两张图，一张 source=dat 正常，另一张 media 只有 kind。根因不在密钥也不在库结构，而是我们自己锁住了自己的副本。src/db/image.py 用进程级全局变量缓存 hardlink.db 连接，Windows 下 sqlite 打开的文件不共享 DELETE，长驻服务一查过图，decrypt_to 的 os.replace 就永久失败（实测同进程持连接时替换报 WinError 5，关掉连接立刻成功；另一进程持有时同样被阻塞），于是 hardlink 副本停在 11:06，之后登记的图片全部查不到。第二层原因：那次收款截图是当天 10:58 才下载的，它的登记行当时还在微信的 WAL 里（3.3MB 未 checkpoint），主库快照本来就没有这一行，11:44 checkpoint 后才写进主库，正好被锁死卡在旧版本上，两件事叠在一起。
- 修复分三处。其一，图片与文件链路改成开-查-关：hardlink 连接每次新建、查完立即关闭，并用 immutable=1 不留 -wal/-shm 旁文件；dir2id 映射按副本 mtime 缓存。其二，刷新遇正本被占用（reason=locked）时改写成旁路副本 <名>.new，读取方统一按 mtime 取最新的一个（LocalSource.path 与 image、media_files 都走 latest_copy），正本恢复可写后自动删掉旁路副本，这样任何进程占着旧副本都不再阻断数据更新。其三，把失败讲清楚：decrypt_to 返回 (bool, reason)，refresh 多给 failed_detail（too_small/read_error/hmac_mismatch/verify_fail/locked）与 shadow，media 多给 missing_reason（no_md5/hardlink_row_missing/hardlink_unreadable/dir_map_missing/file_not_on_disk/no_image_key/decode_failed/voice_model_missing/no_audio/cover_missing/not_requested/too_many_rows）。
